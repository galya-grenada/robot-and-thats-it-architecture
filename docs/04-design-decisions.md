# 04. Архитектурные решения и допущения

| Решение | Почему |
|---|---|
| REST снаружи, gRPC внутри | Браузер не умеет gRPC напрямую; внутри нужны скорость и строгий контракт. Gateway переводит один формат в другой |
| API Gateway без бизнес-логики | Только маршрутизация, проверка токена, перевод протоколов. Логика в шлюзе делает его узким местом и общей точкой изменений |
| Kafka для событий, gRPC для вопросов | Нужен ответ сейчас — gRPC. Произошло событие, кто надо отреагирует — Kafka |
| Хореография вместо оркестратора | Цепочка заказ → оплата → готовка идёт через события, общего управляющего сервиса нет |
| Своя БД у сервиса | Данные одного сервиса не трогают другие; связь только через API и события |
| Один сервис-адаптер на внешнюю систему | Payment ↔ Платёжный сервис, Robots ↔ Роботы, Supply ↔ Склад, Clients ↔ Система лояльности |
| IAM отдельно от Clients | IAM: кто ты и что можно (посетители и персонал). Clients: профиль и бонусы (только посетители) |
| Остатки приходят из Robots в Supply через событие | Supply хранит остатки и пороги сам и решает, когда заказывать |
| Статус заказа хранит Orders | Терминал спрашивает статус через Gateway; Orders обновляет его по событиям |

## Допущения

- API внешних систем неизвестен, поэтому везде принят HTTPS/JSON.
- Рассылку Push/SMS/E-mail выполняет сам Notification Service, сторонний провайдер не детализируется.
- Robots и Tableau Service без БД: Robots — адаптер, Tableau держит только открытые соединения.
